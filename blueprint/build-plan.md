# Build Plan

## MVP

* [x] 1. **Dashboard foundation** - establish the polished Kubernetes operations UI shell, navigation, and resource layout for cluster operations.
* [x] 2. **Cluster overview and mock data** - present overview metrics, workload statuses, namespace controls, and resource tables using realistic placeholder data.
* [x] 3. **Authentication and protected app access** - add local admin login, sessions, and protected routes for the operational application.
* [x] 4. **FastAPI backend foundation** - create the API layer, project structure, and database-backed service foundation for future cluster integration.
* [x] 5. **PostgreSQL application data model** - configure persistent storage for users, sessions, cluster metadata, settings, and operational records.
* [x] 6. **Kubernetes connection and namespace discovery** - connect to a cluster and surface namespaces, endpoints, and resource inventory through the backend.
* [x] 7. **Core resource views** - implement pods, deployments, services, and node listings with status-driven data and real cluster context.
* [x] 8. **Resource details and troubleshooting surfaces** - add detail pages for status, YAML, logs, and recent events for a selected workload or resource.
* [x] 9. **Run app on top of a real Kubernetes cluster (local Minikube)** - deploy the Kubernetes management platform into a real Kubernetes cluster running locally with Minikube.

  * [x] 9a. **Containerize the services** - add reproducible container images and a local Compose runtime for the Next.js frontend, FastAPI backend, and PostgreSQL database.
  * [x] 9b. **Deploy onto Minikube** - add Kubernetes manifests, in-cluster configuration, and RBAC so all three services run as workloads on a local Minikube cluster and the UI operates against the live Kubernetes API.

## Post-MVP

* [x] 10. **Real-time refresh and health updates** - add live refresh behavior, alerting cues, and operational status updates.

* [x] 11. **Live resource metrics and observability** - add real-time CPU, memory, storage, and resource utilization information for nodes and workloads.

  * [x] 11a. **Node metrics** - display live CPU and memory utilization, allocatable capacity, and storage usage for each node.
  * [x] 11b. **Workload metrics** - display CPU and memory usage for Pods and workload resources, with namespace-level utilization summaries.
  * [x] 11c. **Storage metrics** - display node filesystem usage and available storage, with PersistentVolume and PersistentVolumeClaim capacity and utilization where supported.
  * [x] 11d. **Metrics API integration** - integrate the Kubernetes Metrics API and, where needed, Prometheus for historical metrics and advanced observability.
  * [x] 11e. **Metrics UI** - add charts, utilization indicators, time ranges, and resource-level metrics to the dashboard and detail pages.

* [x] 12. **Users, Authentication & RBAC** - database-backed multi-user authentication with exactly three roles (admin/operator/viewer), admin-managed user provisioning (create, role assignment, activate/deactivate, password reset/force change), 15-day password expiration, forced password change, self-service password change, centralized backend permission enforcement, audit logging, and a role-aware admin UI. The previous 12a/12b/12c attempts were rolled back 2026-09-06 and re-speced as this single item (`blueprint/context/current-feature.md`; rollback archives in `blueprint/history/rollbacks/`).

* [x] 13. **Multi-cluster support** - connect and compare multiple Kubernetes environments from one interface.
  * [x] 13a. **Backend cluster store and management API** - seed the default cluster on startup, add list and register cluster endpoints (admin-only create), store kubeconfig references, and lay the database foundation for cluster routing.
  * [x] 13b. **Backend cluster routing** - modify all `/api/v1/cluster/*` routes to accept a `cluster` query param, resolve to the correct `ClusterConnection`, load the appropriate kubeconfig, and return 404/422 for unknown or unreachable clusters.
  * [x] 13c. **Frontend cluster selector** - add a cluster selector dropdown to the header, persist selection to localStorage, and pass the cluster ID on every backend API call.
  * [x] 13d. **Admin cluster management page** - add `/settings/clusters` with a table of registered clusters, a form to register new clusters, and an activate/deactivate toggle (admin-only).

* [x] 14. **AI-Powered SRE/DevOps Assistant** - agentic investigation and human-approved operations using Vercel AI SDK, installed AI Elements, and existing authenticated KubePilot APIs. FastAPI remains the only Kubernetes/Helm integration layer.

  * [x] 14a. **Foundation and UI** — Objective: native streaming assistant at `/assistant`. Files: `app/assistant`, `app/api/assistant`, `components/assistant`, `lib/assistant`, dashboard shell. Backend: reuse session authentication. Frontend: AI Elements conversation/message/prompt/tool components, existing cluster and namespace selection, optional resource/release context. Tools: typed registry foundation. Security: validate every request, configured server-only model, bounded turns and output; no client identity claims. Acceptance: authenticated users can open the assistant, stream replies, cancel, start a new conversation, and see configuration/authentication errors; changing scope starts a fresh conversation.
  * [x] 14b. **Read-only Kubernetes tools** — Objective: inspect live clusters, namespaces, common workloads, nodes, networking, storage, configuration metadata, events, logs, and metrics. Files: backend assistant read/sanitization modules and tool registry. Backend: reuse cluster resolution and Kubernetes clients; add missing read mappings and safe diagnostic projections. Frontend: structured tool results and links. Tools: listClusters, listNamespaces, listResources, inspectResource, getPodLogs, getEvents, getResourceUsage. Security: resources:read, explicit active cluster, bounded results, no raw manifests, environment values, kubeconfig, Secret/ConfigMap contents or credentials. Acceptance: real backend reads are scoped and sanitized; denied/disconnected/missing-resource errors retain safe codes and actionable messages.
  * [x] 14c. **Troubleshooting workflows** — Objective: multi-step evidence-based diagnosis of CrashLoopBackOff, unavailable deployments, scheduling and PVC failures. Files: agent instructions, diagnostics projection, result cards. Backend: owner references, replica/container status, conditions, namespace events and previous/container logs. Frontend: Inspect, View Logs, View Events and Suggest Fix follow-ups. Tools: reuse phase 14b. Security: tool output is untrusted data, never instructions; no shell tool. Acceptance: agent can correlate workload → ReplicaSet/Pod → events/logs, distinguish observations from hypotheses, cite resource scope, and report missing evidence rather than invent causes.
  * [x] 14d. **Human-approved writes** — Objective: confirmed scale/restart and supported resource deletion. Files: backend assistant proposal model/migration/actions, existing management client, Next confirmation route/UI. Backend: durable expiring proposal with actor/session/cluster/arguments, atomic one-use claim, fresh permission checks and audit; reuse deletion service and add narrow scale/restart with UID/resourceVersion preconditions. Frontend: exact target/change review, approve/reject and result states. Tools: proposeScale, proposeRestart, proposeDelete (proposal creation only). Security: LLM has no approval/execution tool; no fabricated transcript approval, replay, cross-session execution, stale scope/object changes or protected namespace bypass. Acceptance: no mutation before explicit confirmation; rejects, stale proposals, viewer access, tampering and replay cause no Kubernetes writes.
  * [x] 14e. **Helm/application lifecycle** — Objective: discovery, install, upgrade, previous-revision rollback and uninstall. Files: assistant tool/action adapters and result cards. Backend: reuse Marketplace, Helm release/repository endpoints and job pipeline. Frontend: repository/package selection through conversation, reviewed proposals, existing background-job links/status. Tools: listHelmReleases, getHelmHistory, listRepositories, searchPackages, getPackage, getJobStatus, proposeInstall, proposeUpgrade, proposeRollback, proposeUninstall. Security: existing marketplace permissions, explicit chart/repository/version, protected namespaces, one-use approvals. Acceptance: approved operations queue real jobs; queued is never displayed as completed; failures and subsequent job state remain observable.
  * [x] 14f. **Observability, auditability and UX** — Objective: operationally useful, tested handoff. Files: assistant UI/status, backend audit/tests, setup documentation. Backend: safe tool audit metadata (tool, actor, scope, duration, result), proposal decision/result records; no prompt/log/credential audit payloads. Frontend: running/success/failed/waiting states, accessible confirmations, loading/empty/error handling, Markdown/code rendering and scoped follow-ups. Tools: reuse prior phases. Security: safe output rendering, cancellation, explicit unknown outcomes, no automatic mutation retry. Acceptance: focused security tests, full backend tests, frontend production build, migration SQL and available runtime smoke checks pass; document any live model/cluster prerequisites.

* [x] 15. **shadcn/ui integration and table migration** - integrate shadcn/ui into the Next.js app and migrate the existing resource tables to reusable shadcn/ui Data Table components while preserving the current visual design.

* [x] 16. **Header components and theme support** - remove the non-functional header search, migrate the header controls (notification, logout) to shadcn/ui components, and add light/dark theme support with a theme switcher while preserving the existing design.

* [x] 17. **UI polish & design consistency** - unify the home, login, and change-password pages onto the dashboard's light palette with simple centered forms, restructure the sidebar into grouped sections (OVERVIEW / WORKLOADS / NETWORK / CONFIGURATION / STORAGE / CLUSTER / ADMINISTRATION) that show only existing resources, rework the header with the KubePilot brand, cluster selector, notifications, and user menu, and design the shell around a `clusterId` context so the future Multi-cluster feature (13) slots in without a redesign.

* [ ] 18. **KubePilot Marketplace** - discover and install Kubernetes Helm packages from Artifact Hub.

  * [x] 18a. **Marketplace navigation & page** - add `/marketplace` route, a main sidebar entry, and a page header (Marketplace - "Discover and install Kubernetes applications") that reuses the existing application shell and preserves current navigation.
  * [x] 18b. **Package discovery** - integrate the Artifact Hub package search API (Helm charts only, kind=0) with pagination/Load More, a reusable PackageCard (logo, name, description, publisher/repository, latest version, Install button), loading skeletons, empty state, and API error state.
  * [x] 18c. **Package search & filtering** - search input connected to the Artifact Hub API with debounce, optional sorting if useful, and correct pagination with loading/empty/error handling.
  * [x] 18d. **Package details** - a lightweight drawer/modal/dedicated view for a package showing name, logo, description, publisher, repository, version, Helm install info, and an Install button.
  * [x] 18e. **Installation configuration dialog** - a reusable dialog collecting package/version/cluster/namespace/release name with validation, reusing the existing cluster and namespace selectors; no Helm command is executed by the frontend.
  * [x] 18f. **Installation API** - POST `/api/marketplace/install` (package_id, version, cluster_id, namespace, release_name) validates request/authorization/cluster/namespace, resolves package/chart metadata, creates an installation job, and returns `{job_id, status: "queued"}` without waiting for Helm.
  * [x] 18g. **Installation job model & background worker** - an InstallationJob model (queued/running/succeeded/failed/cancelled) and a background Helm worker (repo add/repo update/helm install, capture result, update job); do not introduce Celery/RQ unless the existing FastAPI architecture already needs it.
  * [x] 18h. **Installation status API** - GET `/api/marketplace/installations/{job_id}` returning status, package name, cluster, namespace, release name, error_message, and useful timestamps.
  * [x] 18i. **Installation progress UI** - immediate feedback while Helm runs (queued -> running -> succeeded/failed); Close only closes the UI and never cancels the installation.
  * [x] 18j. **Installation history** - a table of recent installations (package, cluster, namespace, status badge, date) with basic status filtering only if easy; no release management/upgrade/rollback/uninstall yet.
  * [x] 18k. **Security & validation** - authenticated user and install-permission checks, cluster/namespace/release-name/package/version validation, never execute arbitrary commands from user input, never trust Artifact Hub metadata as executable input, kube-system protected unless explicitly allowed by policy, safely constructed Helm commands.
  * [ ] 18l. **Marketplace UI polish & responsive** - reuse shadcn/ui components and the Tailwind theme/spacing/colors, responsive package grid, skeleton/empty/error states, dialog animations if already used, mobile/tablet support.
  * [x] 18m. **Release management (backend)** - after an install completes, admins/operators can roll back a release to its previous revision or uninstall (delete) it: job-driven Helm actions (extend InstallationJob with action/revision + worker dispatch, backward-compatible migration), rollback/uninstall endpoints gated by a marketplace release permission (operator + admin), audit events, status through the existing job/progress/history pipeline; no upgrade, no revision picker (helm history), no managing releases the app did not install.
  * [x] 18n. **Release actions UI** - Rollback / Uninstall actions on installation-history rows with confirmation and progress feedback reusing the existing install progress pattern; viewer gets no action controls.

* [x] 19. **Manage resources** - add a "Manage resources" sidebar entry for Kubernetes resource operations and Helm package management in the selected cluster; admins/operators can manage resources, viewers remain read-only, and destructive actions require confirmation, backend permission checks, and audit logging.

  * [x] 19a. **Kubernetes resource management** - add `/manage-resources` and its Kubernetes resources tab, reusing the app shell and selected cluster/namespace controls; list, create through validated YAML, and delete pods, deployments, namespaces, services, and other explicitly supported common resource types, with confirmed deletion targets, loading/empty/error states, backend authorization, and audit records.
  * [x] 19b. **Installed Helm release management** - add a Helm releases tab that discovers releases directly from the selected cluster across namespaces, including releases installed outside KubePilot; show status and revision history, and support confirmed rollback/uninstall through the existing background job, progress, and audit pipeline without requiring a Marketplace install record.
  * [x] 19c. **Helm repository configuration** - add global chart repository configuration under Manage resources (list/add/update/remove KubePilot-managed public URL-only repository connections), with admin/operator mutation permissions, viewer read-only access, validation, audit logging, and shared UI states; repository connections are Helm client configuration, not resources discoverable from a cluster.
  * [x] 19d. **Helm release upgrades** - upgrade installed releases in the selected cluster using an explicitly selected KubePilot-managed repository, chart, and version, with review, backend permission checks, background job progress, and audit logging; resolve and validate the chart source before queuing the existing job pipeline.

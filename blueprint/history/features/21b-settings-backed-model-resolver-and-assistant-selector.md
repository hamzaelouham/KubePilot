# Current Feature

**Feature:** 21b — Settings-backed model resolver and Assistant selector

**Status:** verified

**Branch:** `feature/settings-backed-model-resolver-and-assistant-selector`

## Goal

Allow the authenticated Assistant to select an administrator-registered AI model by its internal database ID while the server resolves the provider, external model ID, configuration, availability, and capabilities from Settings. Present eligible models in a provider-grouped selector without exposing provider credentials or trusting client-supplied provider identities.

## In scope

- Extend the existing Assistant inference contract to accept an internal model UUID or the existing `default` sentinel.
- Resolve a requested model, or the configured default when no selection is supplied, against the persisted `AIModelConfig` and configured provider state.
- Enforce that a selected/default model is enabled, available, backed by a configured provider, and compatible with the current streaming/tool-enabled Assistant runtime.
- Preserve and expose the existing eligible-model capability metadata, including `streaming` and `tools`.
- Add the same-origin Next.js model-list bridge and client schema/helper.
- Add a provider-grouped, accessible Assistant model selector using the existing AI Elements/shadcn selector primitives.
- Keep model loading, empty, denied, stale/unavailable, and unexpected backend/provider errors actionable.

## Out of scope

- Adding providers, changing provider adapters, changing credential encryption, or removing the AI Gateway; those belong to 21a and are already shipped.
- Changing the AI model registry schema or adding a migration unless an existing contract cannot support the internal-ID flow.
- Capability-aware tool attachment, conversational fallback for models without tools, Assistant/provider/tool audit expansion, or broad regression cleanup; those belong to 21c.
- Provider catalog discovery, model creation/editing, default-management UI, model persistence, local-storage selection, or per-user model registries.

## Data / contracts

- `GET /api/v1/assistant/models` remains protected by the existing authenticated `resources:read` boundary and returns `{ models: EligibleModelSummary[] }`. Each item contains the internal UUID `id`, `provider_id`, `provider_name`, `external_model_id`, `friendly_name`, `capabilities` (`streaming`, `tools`, `reasoning`, `vision`, `large_context`), and `is_default`. The client may display the non-secret labels and capability metadata but selects only `id`.
- The Next.js bridge is `GET /api/assistant/models`; it forwards the filtered session cookie, uses `cache: "no-store"`, and preserves safe backend status/message handling.
- The Assistant POST body adds optional `modelId: UUID-string`. Omitted `modelId` maps to the existing `default` runtime sentinel. The Next server validates the UUID; FastAPI remains the authority for existence, provider configuration, enabled/available state, current runtime capability requirements, and external model ID resolution.
- The FastAPI inference payload accepts `model: "default" | UUID`. `default` selects the single database default enforced by the existing partial unique index. A UUID selects only that persisted model. The outbound provider payload always replaces this value with the persisted `external_model_id` and includes no internal ID, credential, or provider configuration from the client.
- A model list can contain only configured-provider, enabled, available records. If no eligible records exist, or no default is configured, the UI does not invent a provider/model default; it explains that an administrator must configure an eligible model, while any returned eligible model can still be selected explicitly. A model disabled or made unavailable after listing is rejected server-side and the UI asks the user to refresh/start a new conversation.
- No database migration is expected: feature 20e already persists the model identity, default, availability, and capability columns used by this contract.
